# get-job 프로젝트 이력서 표현 가이드

2026-09-06 코드 기준. 개인 이력서 원문이 아닌, 구현 사실에 기반한 프로젝트 설명 예시다.
아래의 수치는 설계 제한값이며 실제 정확도 향상률이나 금액 절감률을 뜻하지 않는다.

## 이력서에 붙여 쓸 설명

**get-job — 비용 제어형 LLM 채용 공고 분석 서비스**

Python · FastAPI · PostgreSQL · SQLAlchemy · LangChain Core · LangGraph · Pydantic · React · TypeScript

- 다중 채용 소스의 수집 어댑터와 공통 공고 스키마를 설계하고, 정규화·내용 해시 기반 갱신·변경 스냅샷·교차 소스 중복 그룹화로 채용 데이터 파이프라인 구현.
- 규칙 기반 적합도 산정과 LLM 근거 해석을 분리하고, LangChain Core 프롬프트 구성 및 LangGraph 상태·조건부 분기로 규칙 처리·기본 모델·재검토 모델을 연결.
- 요구사항 우선순위화와 어휘 기반 경력 검색으로 분석 문맥을 선별하고, 입력 크기 제한과 해시 캐시를 적용하여 중복 입력과 재호출을 제한.
- Pydantic 구조 검증과 인용 ID 검증 결과를 재검토 입력에 전달하는 제한형 피드백 워크플로 구현. 수정 최대 1회·공고 1회 분석당 모델 호출 최대 2회의 종료 조건 적용.
- PostgreSQL 조건부 원자적 예산 예약과 호출 원장을 구현하여 동시 요청의 예약 한도를 제어하고, 예약 계획량과 제공자 실사용 토큰을 분리 기록.

## 한 문단 요약

다중 소스 채용 공고를 수집·정규화하고 지원자의 구조화된 경력 근거와 비교하는 서비스 개발.
LangChain Core·LangGraph 기반 조건부 LLM 분석에 어휘 검색, 구조·인용 검증, 최대 1회 수정 피드백을
적용하고, 입력 해시 캐시와 원자적 예산 예약으로 분석 호출량을 관리.

## 적용한 엔지니어링 기법과 근거

| 이력서 용어 | 실제 구현 | 코드 |
|---|---|---|
| 데이터 정규화 / 수집 어댑터 | 소스별 원문을 CollectedJob에 매핑 | crawler/domain.py, crawler/adapters.py, crawler/normalization.py |
| 변경 감지 / 스냅샷 | 내용 해시로 갱신 판단, 변경 내용 저장 | crawler/persistence.py |
| Context engineering | 중복 요구사항 제거, lexical retrieval, 문맥 길이 제한 | budget_analysis.py |
| Conditional model routing | 규칙 0회, 기본 1회, 필요하고 허용된 경우 재검토 1회 | budget_analysis.py |
| Structured output validation | Pydantic 응답 스키마와 요구사항 커버리지 검사 | analysis_pipeline.py |
| Grounding validation | 존재하는 인용 ID와 필수 인용 여부 검사 | analysis_pipeline.py |
| Bounded feedback workflow | 검증 코드 또는 모호한 판정·ID를 review_feedback으로 전달 | budget_analysis.py |
| Content-addressed caching | 입력·규칙 점수·모델·정책 버전 해시로 완료 결과 재사용 | analysis_service.py |
| Atomic budget reservation | DB 조건부 UPDATE, 네트워크 전 예약 커밋 | analysis_budget.py |
| Usage accounting | 모델·단계·상태·예약량·제공자 토큰 기록 | models/ai_usage.py |

코드 경로는 모두 backend/app/ 기준이다. Context engineering은 여기서 "모델에 넣을 근거와 길이를
설계했다"는 뜻으로 사용한다. 벡터 검색이나 학습 기반 검색을 의미하지 않는다.

## 루프 엔지니어링을 설명하는 방식

"Loop engineering"은 최근 사용이 늘어난 넓은 표현이다. 이력서에는 그 이름만 쓰기보다
어떤 피드백과 종료 조건을 구현했는지를 명시하는 것이 설명하기 쉽다.

이 프로젝트의 정확한 표현:

> 루프 엔지니어링의 검증·피드백·종료 조건 원칙을 적용한 최대 1회 수정 워크플로 구현.
> 코드 검증 결과를 후속 모델 입력에 전달하고, 재검증 결과와 호출·예산 한도에 따라 종료하도록 설계.

현재는 순환 엣지 없이 fast → review에 1회 수정 과정을 펼친 고정 워크플로다.
별도 LLM 평가자, 무제한 agent loop, 자동 프롬프트 학습, 도구를 자율 선택하는 에이전트는 아니다.
검증은 JSON·스키마·요구사항·인용 ID 검사와 모호한 판정 비율을 사용한다.
재검토가 같은 자료를 그냥 다시 읽던 v1과 달리 v2는 아래 피드백을 명시적으로 전달한다.

- JSON·스키마 실패: 고정 오류 코드. 잘못된 원문 응답은 전달하지 않음.
- 누락·중복 요구사항, 잘못된 인용: 고정 오류 코드. 검증되지 않은 ID는 전달하지 않음.
- 모호한 매칭: 요구사항 ID·판정·검증된 인용 ID만 전달. 이전 자유 서술은 제외.
- 후속 모델도 같은 원본 근거를 확인. 실패·불확실 시 종료하며 세 번째 호출 없음.

수정 모델이 비어 있거나 허용되지 않으면 실행하지 않는다. 로컬 AI 기본값과 외부 전송 동의 조건도
유지된다. 이 구현을 추가했다고 실제 모델 품질 향상이 확인된 것은 아니다.

## 시스템 아키텍처를 한 문장으로

> React 클라이언트, FastAPI 백엔드, PostgreSQL 저장소를 중심으로 수집·규칙 점수·LLM 분석을
> 모듈로 분리하고, LangGraph가 분석 내부의 상태 전달과 조건부 실행을 담당하도록 설계.

분석의 선택적 모델 경로:

    수집 → 정규화·저장 → 규칙 점수
                        ↓
                  입력 해시 캐시
                        ↓ (미적중)
               요구사항·경력 근거 선별
                        ↓ (해석 필요)
             예산 예약 → 기본 모델 → 코드 검증
                                      ↓ (수정 필요·허용)
                       피드백 + 예산 예약 → 재검토 모델 → 재검증
                                      ↓
                            보고서 · 캐시 · 사용량 원장

## 수치와 표현의 경계

쓸 수 있는 수치: 공고 1회 분석당 모델 호출 최대 2회, 수정 최대 1회, 요구사항 최대 8개,
경력 근거 최대 10개, 입력 기본 12,000바이트, 출력 기본 1,200토큰 요청.

예약량은 보수적 계획 단위이며 실제 과금 토큰·금액의 하드 캡은 아니다.
Codex 출력 한도는 소프트 요청이다. 제공자 응답의 실제 토큰은 별도로 기록한다.
규칙 점수는 AI가 덮어쓰지 않는다.

실측 전에는 쓰지 않을 표현: "비용 50% 절감", "정확도 95%", "환각 제거", "벡터 RAG 구축",
"영속 에이전트 자동 복구", "대규모 MSA 운영". 현재의 오프라인 시험은 가상 입력·고정 응답으로
라우팅과 제한 조건을 검증하며 실제 모델의 의미 정확도를 평가하지 않는다.

## 나중에 공부할 때 먼저 답할 세 질문

1. LangChain Core와 LangGraph는 각각 무엇을 하는가?
   - Core는 질문 메시지 구성, Graph는 상태와 다음 실행 경로 관리.
2. 무엇을 검증하고, 어떻게 수정시키는가?
   - 응답 구조·요구사항 커버리지·인용 ID와 모호한 판정을 확인하고, 짧은 피드백으로 1회 재검토.
3. 왜 호출이 폭증하지 않는가?
   - 규칙 처리·캐시·입력 선별·조건부 라우팅·원자적 예산 예약·최대 2회 종료 조건.

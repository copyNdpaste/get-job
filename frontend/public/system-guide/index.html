02 TWO TOOLS, DIFFERENT JOBS

LangChain과 LangGraph,
이름은 비슷하지만 맡는 일은 달라요.

LLM은 글을 읽고 답하는 모델입니다. 두 라이브러리는 그 모델을 서비스 안에서 사용하기 위한 도구입니다. 여기서는 “질문지”와 “업무 순서표”로 이해하면 쉽습니다.

⌘질문을 구성하는 도구

LangChain Core

“같은 양식의 질문지를 만들어요.”

공고마다 내용은 달라도, 지시·근거·응답 형식을 일정하게 구성합니다. 이 프로젝트는 LangChain 전체 중 Core의 프롬프트·메시지 기능을 사용합니다.

지시제공된 근거 안에서만 비교해 주세요.
재료공고 요구사항 + 선택한 경력 항목
형식판정 · 근거 ID · 이유를 JSON으로
ChatPromptTemplate → 메시지
⑂흐름을 결정하는 도구

LangGraph

“답에 따라 다음 담당자를 정해요.”

현재 결과를 보관하고, 다음 단계를 선택합니다. 규칙으로 끝낼지, 기본 모델을 부를지, 상위 모델에게 한 번 더 검토시킬지 결정합니다.

준비→기본 분석→결과
모호하면 ↳ 재검토 1회 ↗
StateGraph → 노드 + 조건부 연결
LLM내용을 해석설정한 로컬 모델 또는 허용된 원격 모델
+
LangChain Core질문을 구성이 서비스에서 실제 사용하는 범위
+
LangGraph순서와 분기를 실행결과를 다음 단계에 전달
조금 더 정확히: LangChain을 쓰면 LangGraph도 꼭 써야 하나요?

각각 사용할 수 있습니다. LangChain은 모델·도구 통합과 에이전트 구성까지 제공하는 더 넓은 프레임워크이고, LangChain의 에이전트 기능은 LangGraph 위에 구축되어 있습니다. LangGraph는 LangChain 없이도 사용할 수 있습니다.

get-job은 LangChain Core로 메시지를 만들고 LangGraph로 직접 작성한 워크플로를 실행합니다. 모델 연결은 별도의 LocalAIClient, 응답 구조 검사는 Pydantic이 담당합니다.

    무엇을 “모호하다”고 보나요?

    요구사항 중 partial(부분 근거) 또는 인용이 있는 unknown(확인 필요)이 절반 이상이면 재검토 후보입니다. 근거 없는 unknown만으로 상위 모델을 부르지는 않습니다.

    재검토도 확신하지 못한다면?

    확인 필요 상태로 끝냅니다. 새로운 사실을 만들어 채우거나 무한 반복하지 않습니다. 연결 실패도 상위 모델로 전환하는 이유가 되지 않습니다.

    Codex의 출력 제한은 소프트 요청입니다. 숨은 문맥·추론 사용량으로 계획치를 넘을 수 있습니다. 관측한 초과분은 원장에 더해 다음 호출을 제한하지만, 이미 사용한 비용을 취소할 수는 없습니다. 실패한 예약도 자동 반환하지 않습니다.

    다중 채용 소스의 정규화 공고를 분석하는 LangChain Core·LangGraph 워크플로 구현. 규칙 기반 요구사항 추출과 어휘 검색으로 입력 문맥을 줄이고, 근거 검증 결과에 따라 기본 모델과 재검토 모델을 조건부 라우팅. 입력 해시 캐시와 PostgreSQL 원자적 예산 예약으로 공고당 모델 호출을 최대 2회로 제한.

    어디까지 구현되어 있나요?

    구현됨조건부 분석 · 구조·인용 ID 검증 · 완료 보고서 캐시 · DB 예산 예약 · 호출 사용량 기록

    현재 한계단어 검색은 동의어를 놓칠 수 있고, 근거 ID가 실제로 있다는 검증이 의미적 정확성까지 보장하지는 않습니다. 긴 공고는 일부가 생략될 수 있습니다.

    추가 고도화 영역벡터 검색, 중간 체크포인트·영속 작업 큐, 실제 모델의 근거 매칭 정확도·지연·비용 측정. 지금의 가상 라우팅 시험은 실제 성능·비용 절감률의 증거가 아닙니다.
